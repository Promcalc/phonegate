## 1. Назначение

Бэкенд — брокер авторизации по телефону. Внешний сервис (далее — **арендатор**)
просит подтвердить номер телефона пользователя. Бэкенд выбирает свободный номер из пула
арендатора и отдаёт инструкцию: «позвоните на этот номер» или «отправьте SMS с кодом».
Пользователь выполняет действие со своего телефона. Смартфон-шлюз с SIM-картой принимает
звонок или SMS и в ближайшем цикле обмена передаёт событие на бэкенд. Бэкенд сопоставляет
событие с заявкой и сообщает арендатору результат.

Для пользователя арендатор получает готовые ссылки `sms:`/`tel:` с заполненным номером
и кодом, публичную страницу и QR-код. Нажатие ссылки только открывает приложение
пользователя; отправку SMS или звонок подтверждает сам пользователь.

Ключевое ограничение: **бэкенд ничего не отправляет** — ни SMS, ни звонки. Он только
принимает данные от шлюзов и отвечает арендаторам. Расходы оператора — обслуживание SIM;
входящие звонки и SMS на шлюз, как правило, бесплатны. Пользователь платит своему оператору
за исходящий звонок/SMS по своему тарифу.

Дополнительный сценарий — **code-first**: номер пользователя неизвестен заранее. Так
работает Telegram-бот: он просит отправить SMS с кодом на номер шлюза, а бэкенд возвращает
номер отправителя. Подробности — [telegram.md](telegram.md).

## 2. Термины

| Термин | Значение |
|---|---|
| Арендатор (tenant) | Внешний сервис, который использует авторизацию. Имеет API-ключ, пул номеров, лимиты и вебхук. |
| Шлюз (gateway) | Установленное на телефоне приложение PhoneGate с одной или двумя SIM. Идентифицируется токеном. |
| Номер шлюза | SIM-номер, на который пользователь звонит или отправляет SMS. Принадлежит ровно одному арендатору. |
| Пул | Набор номеров шлюзов, выделенный арендатору. |
| Заявка (verification) | Запрос арендатора «подтвердить номер X». Живёт ограниченное время. |
| Событие | Принятая SMS или звонок, пришедшие от шлюза. |
| Совпадение (match) | Событие, сопоставленное с заявкой; после него заявка становится `verified`. |
| RP | Relying party — то же, что арендатор, в терминах OpenID/OAuth. |

## 3. Границы

### 3.1. Входит в объём

- приём событий от существующего Android-приложения без его обязательной доработки;
- автоматическая регистрация номеров шлюзов по данным обмена;
- публичный HTTP API для арендаторов: создание, проверка и отмена заявок;
- публичная страница подтверждения, ссылки `sms:`/`tel:` и QR-код для пользователя;
- режим `code_first`, когда номер неизвестен заранее (Telegram-бот и аналоги);
- исходящие вебхуки арендаторам с подписью и повторами;
- выбор наименее загруженного номера и ротация;
- разделение арендаторов по пулам номеров;
- хранение истории: заявки, события, запросы и ответы API, доставки вебхуков;
- выбор хранилища: память, SQLite, PostgreSQL;
- структурированные логи в stdout;
- сборка одним статическим бинарником, Docker-образ и unit для systemd;
- защита от инъекций, перебора, повторов, подделки и SSRF.

### 3.2. Не входит в объём

- отправка SMS и исходящие звонки со стороны бэкенда;
- биллинг и тарифы арендаторов;
- веб-интерфейс администратора (в v1 — только API и консольные логи);
- мобильное приложение для арендаторов;
- расшифровка записей разговоров в текст;
- long polling и WebSocket в v1 (задел — раздел 7.8);
- гарантированная доставка SMS/звонков (это зона операторов связи);
- замена телефона как фактора для сценариев с высоким риском (см. раздел 19).

## 4. Сценарии

### 4.1. SMS-авторизация

```
Арендатор        Бэкенд                  Шлюз (SIM +79005550001)      Пользователь
   |               |                              |                        |
   |-- POST /verifications {phone:+79001234567} ->|                        |
   |               |-- выбрать номер, код 482913  |                        |
   |<-- 201 {gateway_number, code, ttl} ----------|                        |
   |               |                              |                        |
   |   показывает пользователю: «Отправьте 482913 на +79005550001» ------->|
   |               |                              |<-- SMS 482913 ---------|
   |               |<-- exchange: SMS от +7900... |                        |
   |               |-- сопоставить, verified      |                        |
   |<-- webhook / poll: verified ------------------|                        |
```

1. Арендатор вызывает `POST /api/v1/verifications`, передавая номер пользователя в E.164.
2. Бэкенд нормализует номер, проверяет лимиты, выбирает номер шлюза из пула арендатора,
   генерирует код и создаёт заявку со сроком жизни (по умолчанию 5 минут).
3. Арендатор показывает пользователю номер шлюза и код.
4. Пользователь отправляет SMS с кодом на номер шлюза.
5. Приложение шлюза в очередном цикле обмена отправляет входящую SMS.
6. Бэкенд проверяет отправителя, номер получателя и код, помечает заявку `verified`
   и уведомляет арендатора вебхуком (или арендатор узнаёт статус опросом).

На одном номере шлюза может быть **много активных SMS-заявок одновременно**. Они
различаются кодом: SMS с кодом `482913` подтверждает только заявку с этим кодом на
этом номере шлюза, остальные остаются `pending`. Коды уникальны среди активных
SMS-заявок данного номера шлюза; при генерации коллизия проверяется и код
перегенерируется. Один телефон пользователя тоже может иметь несколько активных
SMS-заявок (до `max_active_sms_per_phone`), если это разные коды/сервисы.

### 4.2. Авторизация звонком (пропущенный вызов)

```
Пользователь --звонит--> Шлюз --сбрасывает/не отвечает--> журнал вызовов
                                                              |
                          Бэкенд <-- exchange: missed call ----+
                             |
                             +--> match по номеру звонящего и активной заявке
```

1. Арендатор создаёт заявку с `method=call` (или `any`).
2. Бэкенд возвращает номер шлюза; код не нужен.
3. Пользователь звонит на номер и сбрасывает вызов. Шлюз не отвечает (в режиме
   авторизации не настроен mp3), вызов фиксируется как пропущенный/отклонённый.
4. Приложение передаёт звонок в обмене; бэкенд сопоставляет его с активной заявкой
   этого номера в пределах окна времени.

Для звонка невозможно передать код, поэтому действует ограничение: **у одного
телефона пользователя на одном номере шлюза не может быть двух активных `call`/`any`
заявок одновременно**. На разных номерах шлюза такие заявки различимы по номеру,
на который звонил пользователь. SMS-заявки этим ограничением не затрагиваются: их
может быть несколько, код различает их.

Повторный `call`/`any` на тот же номер шлюза возвращает `409
verification_already_pending` с существующей заявкой; арендатор может её
переиспользовать или отменить и создать новую.

### 4.3. Смешанный сценарий (`method=any`)

Заявка допускает и SMS, и звонок. В ответе есть и код, и инструкция позвонить.
Подтверждением считается первое подходящее событие. Это удобно, когда пользователь
не может отправить SMS (корпоративный тариф, роуминг) или не может дозвониться.

### 4.4. Code-first: номер неизвестен заранее (Telegram-бот)

```
Пользователь          Бот (арендатор)              Бэкенд                Шлюз
     |                      |                        |                    |
     |-- «привязать номер» ->|                        |                    |
     |                      |-- POST /verifications  |                    |
     |                      |   mode=code_first ---->|                    |
     |                      |<-- номер шлюза + код --|                    |
     |<-- «отправьте SMS ---|                        |                    |
     |    с кодом K7M4...»  |                        |                    |
     |-- SMS с кодом ------------------------------------------------>    |
     |                      |                        |<-- exchange: SMS --|
     |                      |<-- webhook: verified --|                    |
     |                      |    phone=+7900...      |                    |
     |<-- «номер привязан» -|                        |                    |
```

1. Арендатор создаёт заявку с `mode=code_first`; поле `phone` не передаётся.
2. Бэкенд выбирает номер шлюза, генерирует код (по умолчанию 8 символов) и возвращает
   `gateway_number`, `code`, `expires_at`.
3. Бот показывает пользователю инструкцию: отправить SMS с кодом на номер шлюза.
4. Пользователь отправляет SMS со своего телефона.
5. Бэкенд находит активную заявку по коду, извлекает номер отправителя, помечает
   заявку `verified` и возвращает `phone` в вебхуке/ответе.
6. Бот привязывает номер к Telegram-пользователю и подтверждает успех.

Ограничения режима:

- только `method=sms`: звонок не может передать код;
- `phone` в запросе запрещён (`400 phone_not_allowed`);
- код генерирует бэкенд, а не бот; код одноразовый и уникальный среди активных
  SMS-заявок этого номера шлюза;
- до подтверждения `phone` в ответе `null`; после — E.164 отправителя;
- код — bearer-секрет: показывать только в личном чате, не логировать, не пересылать.

Матчинг SMS: текст нормализуется (регистр, пробелы, дефисы), из него извлекается
токен кода; он сравнивается с активными кодами для этого номера шлюза. Код
одноразовый: после совпадения заявка становится `verified`, повторная SMS с тем же
кодом ничего не меняет. Если подходящих активных кодов несколько (аномалия или
нарушение уникального индекса), событие помечается `ambiguous` и заявки не
подтверждаются.

На одном номере шлюза может быть много активных `code_first` заявок. Каждая SMS
разрешает только заявку со своим кодом; остальные остаются `pending` и ждут своих
SMS. Один и тот же отправитель может подтвердить несколько разных заявок разными
SMS, если это разрешено лимитами арендатора.

Полный сценарий для бота, примеры сообщений и чек-лист — [telegram.md](telegram.md).

### 4.5. Ошибки и краевые случаи

| Ситуация | Поведение |
|---|---|
| Номер пользователя не в E.164 | `400 invalid_phone`, заявка не создаётся |
| `phone_first` без `phone` | `400 phone_required` |
| `code_first` с `phone` | `400 phone_not_allowed` |
| `code_first` с `method=call/any` | `400 code_first_sms_only` |
| Нет свободного/живого номера в пуле | `503 no_gateway_available` |
| У телефона уже есть активная `call`/`any`-заявка на этом номере шлюза | `409 verification_already_pending`; для SMS не применяется |
| У телефона несколько активных SMS-заявок | Разрешено в пределах `max_active_sms_per_phone`; код различает заявки |
| SMS с неизвестным кодом | `unmatched` + лимит на отправителя; при нескольких активных заявках нельзя выбрать одну для счётчика |
| Код совпал, но отправитель/номер получателя не тот | `unmatched`, счётчик `attempts` заявки; после 3 — `failed` |
| Истёк TTL | `expired`, вебхук `verification.expired` |
| Позвонил/прислал SMS другой номер | Событие сохраняется как `unmatched`, заявка не меняется |
| Caller ID скрыт | Событие `unmatched`; в инструкции рекомендуется SMS |
| Шлюз офлайн | Номер не выбирается; при создании — `503` |
| Дубликат события при повторе обмена | Отбрасывается по ключу дедупликации |
| Вебхук арендатора недоступен | Повторы с backoff; статус доступен опросом |
| Арендатор отменил заявку | `cancelled`; последующие события не подтверждают её |

## 5. Функциональные требования

| ID | Требование |
|---|---|
| FR-1 | Бэкенд принимает обмен от приложения по существующему контракту `POST /exchange` и не требует доработки приложения для базового сценария. |
| FR-2 | Ответ на обмен в режиме авторизации — пустой (`204` или `{}`); команды на отправку SMS/звонков не выдаются. |
| FR-3 | Номера шлюзов регистрируются автоматически по ключам в запросе обмена; администратор подтверждает их и распределяет по пулам. |
| FR-4 | Арендатор создаёт заявку через API, получает номер шлюза, код (для SMS) и срок жизни. |
| FR-5 | Заявка подтверждается входящей SMS с верным кодом или входящим/пропущенным звонком с номера пользователя. |
| FR-6 | Статус заявки доступен опросом и вебхуком; вебхук подписан и повторяется при ошибках. |
| FR-7 | Каждый номер шлюза принадлежит ровно одному арендатору; пересечение пулов запрещено конфигурацией. |
| FR-8 | Номер выбирается по наименьшей загрузке с ротацией; повторная заявка того же номера по возможности сохраняет номер. |
| FR-9 | Хранилище переключается между памятью, SQLite и PostgreSQL; в БД есть история заявок, событий, API-вызовов и вебхуков. |
| FR-10 | Все логи пишутся в stdout структурированно; секреты и коды в логи не попадают. |
| FR-11 | Поставка — один бинарник; Docker-образ запускается на пустом контейнере с томом для данных. |
| FR-12 | Входные данные валидируются по схеме, размеру, форматам и лимитам; SQL только параметризованный. |
| FR-13 | Ограничения частоты действуют на арендатора, номер пользователя, IP и шлюз. |
| FR-14 | Административный API позволяет смотреть историю, подтверждать номера и управлять шлюзами. |
| FR-15 | Конфигурация читается из YAML/JSON, поддерживает переменные окружения и горячую перезагрузку безопасных частей. |
| FR-16 | При включённых `links` ответ на создание/повтор содержит `sms:`, `tel:`, `page_url`, `qr_url`; публичная страница и QR доступны без API-ключа, но по подписанному TTL-токену. |

## 6. Архитектура

### 6.1. Компоненты

```
                    HTTPS                        HTTPS
  Арендатор  <---------------->  +----------------------------+
  (backend)                     |  phonegate-server           |
                                |                             |
  Браузер пользователя          |  api/       публичный API   |
  (через backend арендатора)    |  gateway/   протокол шлюза  |
                                |  admin/     админ-API       |
                                |  web/       страница и QR   |
                                |  core/      заявки, матчинг |
                                |  pool/      выбор номеров   |
                                |  store/     memory|sqlite|pg |
                                |  webhook/   доставка        |
                                +-------------+---------------+
                                              ^
                                              | HTTPS, токен шлюза
                                +-------------+---------------+
                                |  Android PhoneGate (шлюз)   |
                                |  SIM1 / SIM2, SMS, звонки   |
                                +-----------------------------+
```

Один процесс, без брокеров и внешних очередей. Фоновые задачи (истечение заявок,
повторы вебхуков, очистка истории) выполняются внутри процесса с блокировкой в БД,
чтобы несколько экземпляров не дублировали работу.

### 6.2. Технологический стек

- Go 1.23+; один статический бинарник `CGO_ENABLED=0`.
- HTTP: стандартная библиотека + `chi` (или `net/http` с ручным роутингом).
- SQLite: `modernc.org/sqlite` (pure Go), WAL, один писатель.
- PostgreSQL: `pgx`; опционально для HA.
- Конфигурация: YAML (`gopkg.in/yaml.v3`, `KnownFields(true)`) с подстановкой `${ENV}`.
- Логи: `log/slog`, JSON в stdout.
- Метрики: Prometheus (`/metrics`), опционально отдельный порт.
- QR: `github.com/skip2/go-qrcode` (чистый Go, PNG); HTML — `html/template`.
- Криптография: `crypto/rand`, `crypto/hmac`, `crypto/sha256`, `crypto/subtle`.
- Никаких shell-вызовов, динамического SQL и внешних CDN.

### 6.3. Поток обработки события

1. Аутентификация шлюза по токену, проверка IP (если настроено).
2. Разбор и валидация тела; невалидные отдельные записи отбрасываются с логом,
   корректные — обрабатываются (чтобы «плохая» запись не блокировала очередь).
3. Дедупликация по естественному ключу.
4. Сохранение события.
5. Поиск подходящей заявки и матчинг.
6. При успехе — транзакция: `verified` + запись в очередь вебхуков.
7. Ответ шлюзу `204`/`{}`; курсор на устройстве сдвигается.

## 7. Протокол смартфона

### 7.1. Совместимость

Бэкенд реализует контракт [../api/openapi.yaml](../api/openapi.yaml) без изменений:

- `POST /exchange` — приём SMS и звонков, ответ с командами;
- `POST /outgoing-report` — приём отчёта об исходящих (если URL задан).

Пути настраиваются, поэтому в конфигурации бэкенда они задаются явно.

### 7.2. Идентификация шлюза

Приложение не передаёт идентификатор устройства. Шлюз идентифицируется **токеном
в заголовке авторизации**:

```
Authorization: Bearer <gateway_token>
```

Токен — случайные 32 байта, в конфигурации хранится SHA-256. Один токен = один шлюз =
один пул = один арендатор. Если приложение использует другое имя заголовка, бэкенд
поддерживает список допустимых имён (`gateway.auth_headers`), но рекомендуется
`Authorization`.

Неизвестный токен → `401`; приложение повторит запрос, оператор должен исправить
настройки. Отключённый шлюз → `403` с кодом `gateway_disabled`.

### 7.3. Автоматическая регистрация номеров

Ключи верхнего уровня в запросе обмена — номера SIM. При каждом обмене бэкенд:

1. нормализует ключ в E.164;
2. ищет номер в таблице `gateway_numbers`;
3. если номера нет и `auto_register_numbers=true` — создаёт запись со статусом
   `pending` (или `active`, если `require_approval=false`) в пуле шлюза; если пул
   шлюза не задан, номер остаётся `unassigned` и в авторизации не участвует;
4. если номер закреплён за другим шлюзом — пишет WARN и не меняет владельца
   (защита от подмены); перенос возможен только явной командой администратора;
5. если номер невалиден — пишет WARN и игнорирует ключ.

Так выполняется требование «не вводить номера на сервисе»: оператор один раз указывает
номер в настройках приложения (Android часто не отдаёт номер SIM программно), а бэкенд
подхватывает его из первого обмена и дальше использует автоматически.

**Ограничение Android.** Приложение берёт номер из настроек, а не из SIM. Если номер
указан неверно, события будут приписаны чужому номеру. Поэтому: (а) в приложении нужна
проверка формата и подсказка; (б) бэкенд показывает номер в админ-API и позволяет
заблокировать; (в) в будущей версии приложения — передача `subscriptionId`, `carrier`,
`phoneNumber` (если доступен) и подтверждение номера администратором.

### 7.4. Ответ шлюзу

В режиме авторизации бэкенд **всегда** отвечает без команд:

```
HTTP/1.1 204 No Content
```

Пустой JSON `{}` также допустим. Это гарантирует, что сервис не тратит деньги
на исходящие SMS/звонки.

Если в будущем появятся другие функции (уведомления, исходящие), они включаются
отдельным флагом и не относятся к авторизации.

### 7.5. Валидация запроса обмена

- `Content-Type: application/json`, тело ≤ 1 МиБ.
- Максимум 4 номера верхнего уровня, 500 SMS и 1000 звонков на запрос.
- Телефоны — строки ≤ 32 символов; текст SMS ≤ 4096; время — RFC 3339 с оффсетом.
- `sync_id` — UUID ≤ 64 символов.
- Неизвестные поля игнорируются (прямая совместимость с будущими версиями приложения).
- Ошибка структуры (не JSON, нет `sync_id`) → `400`; ошибка отдельной записи → запись
  отбрасывается, запрос принимается, чтобы не зациклить повторы.

### 7.6. Дедупликация

Естественный ключ события:

```
sha256(gateway_id | kind | peer_phone | event_time | direction | text_hash | duration)
```

Дополнительно учитывается `sync_id`: повторная доставка того же окна не создаёт
дубликатов. Уникальный индекс в БД защищает от гонок. Событие, уже привязанное
к заявке, повторно не матчится.

### 7.7. Желаемые доработки приложения (не блокируют v1)

| Доработка | Зачем |
|---|---|
| `gateway_id` в заголовке или теле | точная идентификация без привязки к токену |
| Серверный интервал опроса | выставить 5 с для авторизации без ручной настройки |
| Режим «авторизация» для входящих | не отвечать, не играть mp3, не записывать; сразу сбрасывать |
| Передача `_id` SMS/звонка | надёжная дедупликация вместо эвристики |
| Отправка номера SIM из `SubscriptionInfo` | меньше ручного ввода |
| HMAC-подпись запроса | защита от подмены при утечке токена |
| Long-poll/WebSocket | после v1: меньше задержка и трафик; в v1 не используем |

### 7.8. Транспорт v1

В первой версии — только простые запросы, без удержания соединений:

- **Шлюз** раз в N секунд отправляет `POST /exchange` с накопленными SMS и звонками
  и получает пустой ответ. Для авторизации интервал — 5 секунд. Курсор и `sync_id`
  работают как в текущем приложении; доработка приложения не требуется.
- **Бот/внешний сервис** создаёт заявку через `POST /verifications`, а результат
  получает вебхуком (предпочтительно) или периодическим `GET /verifications/{id}`
  с паузой `poll_after_ms`.
- **Long polling и WebSocket** в v1 не используются. Это упрощает прокси, таймауты,
  реконнекты и отладку; доменный API от транспорта не зависит.
- Задел на будущее: отдельный `GET /gateway/wait` или WebSocket для команд/конфига,
  плюс, при необходимости, `GET /verifications/{id}?wait=30` для арендаторов без
  вебхука. Это добавляется без изменения модели заявок.

## 8. Публичный API арендатора

База: `https://<host>/api/v1`. Формат — JSON UTF-8. Аутентификация — заголовок
`Authorization: Bearer <tenant_api_key>`; опционально HMAC-подпись (раздел 14.3).

Заголовок `X-Request-Id` принимается и возвращается; если не передан — генерируется.

### 8.1. Создание заявки

`POST /verifications`

Заголовки:

- `Authorization: Bearer ...`
- `Idempotency-Key: <uuid>` — обязателен для повторных вызовов; хранится 24 часа.

Тело:

```json
{
  "mode": "phone_first",
  "phone": "+79001234567",
  "method": "sms",
  "purpose": "login",
  "locale": "ru",
  "ttl_seconds": 300,
  "metadata": {
    "user_id": "42",
    "ip": "203.0.113.10"
  }
}
```

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `mode` | enum | нет | `phone_first` (по умолчанию) или `code_first` |
| `phone` | string | да для `phone_first` | Номер пользователя; нормализуется в E.164; для `code_first` запрещён |
| `method` | enum | нет | `sms` (по умолчанию), `call`, `any`; для `code_first` только `sms` |
| `purpose` | string | нет | `login`, `signup`, `confirm`, `recovery`, `telegram_bind`; для статистики |
| `locale` | string | нет | `ru`, `en`; язык `instructions` |
| `ttl_seconds` | int | нет | 60…900; по умолчанию из конфигурации |
| `metadata` | object | нет | ≤ 4 КиБ, возвращается как есть; не логируется целиком |
| `callback_url` | string | нет | Переопределение вебхука; только из allowlist арендатора |

Ответ `201 Created`:

```json
{
  "id": "vrf_01JABCDEFGHJKMNPQRSTVWXYZ0",
  "mode": "phone_first",
  "status": "pending",
  "method": "sms",
  "phone": "+79001234567",
  "gateway_number": "+79005550001",
  "code": "482913",
  "instructions": "Отправьте SMS с кодом 482913 на номер +79005550001",
  "created_at": "2026-10-21T12:00:00Z",
  "expires_at": "2026-10-21T12:05:00Z",
  "poll_after_ms": 3000,
  "links": {
    "sms_uri": "sms:+79005550001?body=482913",
    "sms_uri_ios": "sms:+79005550001&body=482913",
    "tel_uri": null,
    "page_url": "https://auth.example.com/v/vt_01JABCDEFGHJKMNPQRSTVWXYZ0",
    "qr_url": "https://auth.example.com/v/vt_01JABCDEFGHJKMNPQRSTVWXYZ0/qr.png"
  },
  "metadata": {"user_id": "42"}
}
```

Для `method=call` поля `code` нет, инструкция: «Позвоните на номер … и сбросьте вызов».
Для `any` есть и код, и обе инструкции. Для `code_first` `phone` до подтверждения
равен `null`, а `code` — сгенерированный сервером код (8 символов).

`links` — ссылки для пользователя. Объект возвращается только в ответе на создание
и повтор заявки: SMS-ссылки содержат одноразовый код, поэтому в `GET` их нет. Клиент
должен сохранить ссылки; поля описаны в 8.7.

Ошибки: `400 invalid_phone|invalid_request|phone_required|phone_not_allowed|code_first_sms_only`,
`401 unauthorized`, `403 forbidden`, `409 verification_already_pending`,
`429 rate_limited`, `503 no_gateway_available`.

При `409` в теле возвращается существующая заявка, чтобы арендатор мог её показать;
`links` в ней нет — используйте ранее сохранённые ссылки или `retry`.
Флаг `replace=true` (query) отменяет конфликтующую `call`/`any`-заявку на этом номере
шлюза и создаёт новую; для SMS он не требуется. Использовать осознанно.

На одном номере шлюза может быть много активных SMS-заявок: и `phone_first`, и
`code_first`. Код уникален среди активных SMS-заявок этого номера шлюза, поэтому SMS
однозначно выбирает заявку. Для одного телефона действует `max_active_sms_per_phone`
(по умолчанию 10); для `code_first` до первого совпадения телефон неизвестен, поэтому
действуют `max_active_per_tenant` и `max_pending_per_number`.

Для `call`/`any` — не более одной активной заявки на пару «телефон + номер шлюза»;
повтор возвращает `409 verification_already_pending`. Для SMS `409` возможен только
при конфликте `Idempotency-Key`, а не из-за другой активной заявки.

### 8.2. Статус заявки

`GET /verifications/{id}`

Ответ `200`:

```json
{
  "id": "vrf_01JABCDEFGHJKMNPQRSTVWXYZ0",
  "mode": "phone_first",
  "status": "verified",
  "method": "sms",
  "phone": "+79001234567",
  "gateway_number": "+79005550001",
  "created_at": "2026-10-21T12:00:00Z",
  "expires_at": "2026-10-21T12:05:00Z",
  "verified_at": "2026-10-21T12:01:17Z",
  "reason": null,
  "metadata": {"user_id": "42"}
}
```

`status`: `pending`, `verified`, `expired`, `cancelled`, `failed`.
`reason` для `failed`: `too_many_attempts`, `gateway_error`, `rejected`.
Код возвращается только в ответе на создание заявки; в `GET` его нет, чтобы не хранить
код в открытом виде. По той же причине в `GET` нет `links`: SMS-ссылки содержат код.
Клиент сохраняет `links` из ответа на создание/повтор. Для `code_first` поле `phone`
равно `null` до подтверждения и заполняется номером отправителя после совпадения.

Кэширование: `Cache-Control: no-store`.

### 8.3. Отмена

`POST /verifications/{id}/cancel`

Ответ `200` с заявкой в статусе `cancelled`. Повторная отмена идемпотентна.
Отменить можно только `pending`.

### 8.4. Повтор

`POST /verifications/{id}/retry`

Создаёт новую заявку с тем же номером, пулом и метаданными, но новым кодом и TTL.
Старая помечается `cancelled`. Для `code_first` номер ещё неизвестен, поэтому
создаётся новый код, а `phone` остаётся `null`. Ответ — новая заявка с новыми `links`.
Старые `page_url`/`qr_url` после `retry` недействительны: страница проверяет статус
старой заявки. Ограничение: не чаще `retry_interval` (по умолчанию 30 с) на одну заявку.

### 8.5. Список заявок

`GET /verifications?mode=code_first&status=pending&phone=...&from=...&to=...&limit=50&cursor=...`

Только заявки своего арендатора. Пагинация курсором, максимум 200. Нужен для
поддержки и сверки; для высоких нагрузок — выключить или ограничить.

### 8.6. Служебные

- `GET /me` — арендатор, лимиты, пулы, версия.
- `GET /healthz` — живость процесса (без БД).
- `GET /readyz` — готовность (БД, конфигурация).
- `GET /metrics` — Prometheus; по умолчанию только на localhost/отдельном порту.

### 8.7. Ссылки, QR и публичная страница

В ответе на создание заявки (и на повтор) есть объект `links`:

| Поле | Когда есть | Что содержит |
|---|---|---|
| `sms_uri` | `method=sms` или `any` | `sms:<номер>?body=<URL-encoded код>` по RFC 5724; Android и большинство клиентов |
| `sms_uri_ios` | `method=sms` или `any` | `sms:<номер>&body=<URL-encoded код>`; вариант для iOS, где `?body` может не сработать |
| `tel_uri` | `method=call` или `any` | `tel:<номер>` по RFC 3966; открывает dialer, но не звонит сам |
| `page_url` | при `links.enabled` | HTTPS-страница для кнопки Telegram и для браузера |
| `qr_url` | при `links.enabled` | PNG с QR-кодом: `sms_uri` для `sms`/`any`, `tel_uri` для `call` (совместимость) |
| `sms_qr_url` | `method=sms` или `any` | PNG с QR-кодом на HTTPS-страницу `/go/sms` с кнопкой открытия SMS |
| `tel_qr_url` | `method=call` или `any` | PNG с QR-кодом на HTTPS-страницу `/go/call` с кнопкой звонка |

Пример:

```json
{
  "sms_uri": "sms:+79005550001?body=482913",
  "sms_uri_ios": "sms:+79005550001&body=482913",
  "tel_uri": null,
  "page_url": "https://auth.example.com/v/vt_01JABCDEFGHJKMNPQRSTVWXYZ0",
  "qr_url": "https://auth.example.com/v/vt_01JABCDEFGHJKMNPQRSTVWXYZ0/qr.png",
  "sms_qr_url": "https://auth.example.com/v/vt_01JABCDEFGHJKMNPQRSTVWXYZ0/qr.png?kind=sms",
  "tel_qr_url": null
}
```

Для `code_first` доступен только `sms_uri`/`sms_uri_ios`: звонок не передаёт код.
Для `method=any` есть и SMS, и звонок; демо и публичная страница используют
`sms_qr_url` и `tel_qr_url`, поэтому QR-коды различаются. `qr_url` оставлен для
совместимости: он содержит raw `sms:`/`tel:`, который некоторые камеры Android
показывают простым текстом.
Если `links.enabled=false`, объекта `links` нет; остаются `instructions`, номер и код.

#### Токен ссылки

`page_url` и `qr_url` используют один короткоживущий токен:

```
page_url = ${server.public_url}${links.page_path}/{token}
qr_url   = ${page_url}/qr.png

payload = {"v":1,"sid":"vrf_...","code":"482913","exp":1760000000}
token   = base64url(payload) + "." + base64url(HMAC-SHA256(payload, links.secret))
```

- Токен подписан, но не зашифрован: он является bearer-секретом. Не логировать его
  целиком; в access-логах оставлять только префикс.
- TTL токена равен TTL заявки. После истечения страница и QR отдают `410 link_expired`.
- В токене нет телефона пользователя, метаданных и текста SMS. Для `call` поле `code`
  отсутствует.
- Подпись проверяется до обращения к БД; `sid` и `code` дополнительно сверяются с
  заявкой и хэшем кода.
- Секрет `links.secret` одинаковый на всех инстансах; при ротации старые ссылки
  перестают работать.

#### Публичные endpoints

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/v/{token}` | HTML-страница подтверждения, `text/html; charset=utf-8` |
| `GET` | `/v/{token}/qr.png` | PNG QR-код, `Content-Type: image/png`; `?kind=sms|call` — действие |
| `GET` | `/v/{token}/go/{kind}` | HTTPS-страница с кнопкой открытия SMS/звонка |
| `GET` | `/v/{token}/status` | JSON статуса для автообновления страницы |

Правила:

- Без API-ключа: доступ по токену; rate limit на IP и токен (по умолчанию 60/мин).
- `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`.
- Страница не рендерит `metadata`, не показывает полный номер пользователя и не
  содержит сторонних скриптов. CSP — только собственные стили/скрипты.
- `status` возвращает `status`, `expires_at`, `verified_at` и маскированный телефон;
  код и `metadata` не возвращает:

  ```json
  {"status":"pending","expires_at":"2026-10-21T12:05:00Z","verified_at":null,"phone_masked":"+7900***4567"}
  ```

- Язык страницы — `locale` заявки (`ru`/`en`), по умолчанию `ru`.
- QR генерируется на лету; размер и коррекция ошибок — в конфиге. Для `sms`/`any`
  при `?kind=sms` внутри QR HTTPS-страница `/go/sms`, для `call`/`?kind=call` —
  `/go/call`. Без `kind` сохраняется совместимость: raw `sms_uri`/`tel_uri`.
  Сканирование только открывает композер/dialer; отправку или звонок подтверждает
  пользователь.
- Камера Android и часть QR-ридеров не открывают raw `sms:`/`tel:`, а показывают
  их текстом. Поэтому демо и публичная страница используют QR на HTTPS-страницу:
  она пытается открыть приложение автоматически и всегда показывает кнопку
  «Открыть приложение SMS»/«Открыть телефон» как fallback.
- Страница на телефоне показывает кнопки «Отправить SMS» (`sms_uri` или `sms_uri_ios`)
  и «Позвонить» (`tel_uri`), кнопки копирования кода и номера. На десктопе — QR
  и инструкция открыть страницу на телефоне.
- В Telegram WebView кастомные схемы могут блокироваться. Страница определяет это и
  показывает «Открыть в браузере» и копирование; основной сценарий не должен зависеть
  от того, что `sms:`/`tel:` откроются внутри Telegram.
- В Telegram код отправляется в `<code>...</code>`: по нажатию клиенты копируют его.
  Кнопка «Открыть страницу» — это `page_url` (inline URL, только HTTP/HTTPS).

#### Приватность и злоупотребления

- Ссылка действует до TTL заявки, но её можно переслать. Поэтому TTL короткий, а
  бот/сервис обязан сверять `telegram_user_id`/пользователя перед привязкой.
- Нельзя считать переход по ссылке или нажатие «Отправить» подтверждением: статус
  меняется только по событию от шлюза.
- Для `phone_first` в ссылке нет номера пользователя; для `code_first` номер появляется
  только после SMS.
- Ошибки страницы: `404` — токен не найден/неверная подпись; `410` — истёк TTL или
  заявка отменена. Тексты ошибок не раскрывают, существует ли заявка.

### 8.8. Коды ошибок

Единый формат:

```json
{
  "error": {
    "code": "rate_limited",
    "message": "Слишком много запросов",
    "request_id": "req_...",
    "retry_after_ms": 60000
  }
}
```

| HTTP | code | Когда |
|---|---|---|
| 400 | `invalid_request` | Невалидный JSON/поля |
| 400 | `invalid_phone` | Номер не E.164/не разрешён |
| 400 | `phone_required` | `phone_first` без номера |
| 400 | `phone_not_allowed` | `code_first` с номером |
| 400 | `code_first_sms_only` | `code_first` с `call`/`any` |
| 401 | `unauthorized` | Нет/неверный ключ |
| 403 | `forbidden` | IP не в allowlist, арендатор выключен |
| 404 | `not_found` | Заявка не найдена или чужая |
| 409 | `verification_already_pending` | Активная `call`/`any`-заявка у пары «телефон + номер шлюза» |
| 409 | `idempotency_conflict` | Тот же ключ, другое тело |
| 410 | `link_expired` | Публичная страница/QR: истёк TTL или заявка отменена |
| 429 | `rate_limited` | Превышен лимит |
| 503 | `no_gateway_available` | Нет живого номера |
| 500 | `internal` | Внутренняя ошибка (без деталей) |

## 9. Вебхуки

### 9.1. События

| Событие | Когда |
|---|---|
| `verification.verified` | Заявка подтверждена |
| `verification.expired` | Истёк TTL |
| `verification.failed` | Превышены попытки или ошибка |
| `verification.cancelled` | Отменена арендатором |

### 9.2. Запрос

```
POST <callback_url>
Content-Type: application/json
X-PhoneGate-Event: verification.verified
X-PhoneGate-Delivery-Id: whd_01J...
X-PhoneGate-Timestamp: 1761048000
X-PhoneGate-Signature: v1=<hex hmac_sha256(secret, timestamp + "." + raw_body)>
```

```json
{
  "event": "verification.verified",
```

### 9.3. Правила доставки

- Только HTTPS в production; HTTP допустим лишь при `allow_insecure_webhooks=true`.
- Таймаут 10 с, максимум 5 попыток: 1 с, 5 с, 30 с, 2 мин, 10 мин.
- Успех — любой `2xx`; `3xx` не преследуются; `4xx` кроме `429` — окончательная ошибка.
- Подпись проверяется арендатором; повторная доставка имеет тот же `delivery_id`,
  арендатор должен быть идемпотентен.
- При исчерпании попыток — запись в БД со статусом `failed`, метрика, лог.
- Вебхук не является единственным способом: статус всегда доступен через `GET`.

### 9.4. SSRF-защита

- URL вебхука берётся только из конфигурации или allowlist арендатора, не из
  произвольного поля запроса.
- Запрещены `localhost`, link-local, private ranges и metadata-адреса, если не разрешено
  явно (`webhook.allow_private=false`).
- DNS резолвится перед подключением; проверка повторяется после редиректа.
- Редиректы по умолчанию запрещены.

## 10. Административный API

Отдельный префикс `/admin/api/v1`, отдельный токен (`admin_token_hash`), опционально
отдельный порт и IP allowlist. Все действия пишутся в `audit_log`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/gateways` | Список шлюзов, последняя связь, версия, статус |
| POST | `/gateways/{id}/disable` | Отключить шлюз |
| POST | `/gateways/{id}/enable` | Включить |
| GET | `/numbers` | Номера, владелец, пул, статус, последнее событие |
| POST | `/numbers/{e164}/approve` | Подтвердить номер и назначить пул |
| POST | `/numbers/{e164}/pool` | Перенести номер в другой пул |
| POST | `/numbers/{e164}/disable` | Заблокировать номер |
| GET | `/verifications` | Заявки с фильтрами |
| GET | `/verifications/{id}` | Детали, включая события |
| GET | `/events` | Входящие SMS/звонки, фильтры по шлюзу/номеру/дате |
| GET | `/api-calls` | История запросов/ответов арендаторов (без секретов) |

передаётся URL-кодированным (`%2B7900...`).

## 11. Конфигурация

### 11.1. Формат

YAML (JSON — совместимое подмножество). Полный пример — [config.example.yaml](config.example.yaml).
Правила:

- `version: 1`; неизвестные поля — ошибка запуска (`KnownFields`).
- Подстановка `${VAR}` и `${VAR:-default}`; секреты можно читать из файлов
  (`*_file`), чтобы не хранить в репозитории.
- Валидация при старте: уникальность номеров между арендаторами, существование пулов,
  длина секретов ≥ 32 байта, корректность E.164, HTTPS для вебхуков; при
  `links.enabled` — `links.secret` ≥ 32 байт и `server.public_url` (для Telegram — HTTPS).
- Горячая перезагрузка по `SIGHUP`/`POST /admin/reload`: арендаторы, пулы, лимиты,
  уровень логов. Хранилище и порт — только рестарт.
- При ошибке конфигурации процесс не стартует (fail fast), в лог — понятная причина.

### 11.3. Секреты

- API-ключи и токены шлюзов хранятся только как SHA-256 (или HMAC с солью).
- Вебхук-секрет нужен в открытом виде для подписи; хранить в env/secret-файле.
- `links.secret` — HMAC-ключ для публичных ссылок; одинаковый на всех инстансах,
  хранится только в env/secret-файле. При утечке ссылки можно отозвать, сменив ключ
  (все активные ссылки при этом перестанут работать).
- В логи и админ-API секреты не попадают; в ответах — только префикс ключа.
- Ротация: два активных ключа на арендатора, старый отключается после перехода.

## 12. Хранение данных

### 12.1. Режимы

| Режим | Плюсы | Минусы | Когда |
|---|---|---|---|
| `memory` | Нет файлов, приватно, быстро | Всё теряется при рестарте; нет истории | Демо, тесты, разовый запуск |
| `sqlite` | Один файл, бэкап копированием, без внешних сервисов | Один писатель, не для HA | Малый и средний объём (по умолчанию) |
| `postgres` | HA, реплики, конкурентная запись | Нужен внешний сервер | Несколько экземпляров, большой объём |

При `memory` предупреждение в логе: незавершённые заявки будут потеряны.
Переключение режима не мигрирует данные автоматически.

### 12.2. Схема (SQLite/PostgreSQL)


Индексы: `sessions(tenant_id, phone_e164, status)`, `sessions(status, expires_at)`,
уникальный частичный `sessions(gateway_number, code_hash) WHERE status='pending' AND code_hash IS NOT NULL`,
уникальный частичный `sessions(phone_e164, gateway_number) WHERE status='pending' AND method IN ('call','any') AND phone_e164 IS NOT NULL`,
`events(gateway_number, event_time)`, `events(session_id)`, `webhook(status, next_attempt_at)`,
`api_calls(tenant_id, created_at)`.

Первый индекс не даёт двум активным SMS-заявкам на одном номере иметь одинаковый код.
Второй — не даёт двум активным `call`/`any`-заявкам одного телефона висеть на одном
номере шлюза. Для `code_first` телефон до совпадения `NULL`, поэтому второй индекс
начинает действовать только после подтверждения (для `code_first` звонок запрещён).

Публичные ссылки не добавляют колонок: `page_url`/`qr_url` — HMAC-токен с `id`,
кодом и `exp`; в БД по-прежнему хранится только хэш кода. Токен живёт не дольше
заявки и не пишется в логи.

### 12.3. Что хранится и сколько

- Заявки — 30 дней (настраивается), затем удаляются или анонимизируются.
- События — 7 дней сырыми; дольше — только агрегаты (если включено).
- Тексты SMS — опционально (`store_sms_text`), по умолчанию **не хранятся** после
  матчинга: сохраняется хэш и факт совпадения. Это снижает риск утечки кодов.
- API-вызовы — 7 дней, тела редактируются: коды, токены, секреты заменяются на `***`.
- Вебхуки — 30 дней; тела не хранятся, только статус и ошибка.
- Аудит — 1 год.
- В `memory` истории нет; в логах — только текущая сессия.

### 12.4. Бэкапы и миграции

- SQLite: `VACUUM INTO '/backup/phonegate-YYYYMMDD.db'` по расписанию; WAL.
- PostgreSQL: стандартные бэкапы; миграции встроены в бинарник (`schema_migrations`).
- Миграции применяются при старте; при несовместимости — отказ старта с понятным логом.
- Экспорт истории — админ-API (CSV/JSON) с ограничением объёма.

## 13. Выбор номера и балансировка

### 13.1. Кандидаты

Номер попадает в выборку, если:

- принадлежит пулу арендатора;
- `status=active`;
- шлюз `active` и `last_seen_at > now - gateway.offline_after`;
- `pending_sessions < verification.max_pending_per_number`;
- номер не в cooldown после ошибок.

### 13.2. Алгоритм `least_loaded`

1. Если у телефона пользователя уже есть активная заявка в этом пуле и `sticky=true`,
   по возможности вернуть номер этой заявки, если он не переполнен и не создаёт
   конфликт `call`/`any` на том же номере. Иначе выбрать другой номер.
2. Иначе отсортировать кандидатов:
   1. по числу активных заявок (по возрастанию);
   2. по числу событий за последние 5 минут (по возрастанию);
   3. по `last_assigned_at` (сначала давно не использованные — ротация).
3. Взять первый; обновить `last_assigned_at`.

Дополнительно можно задать `max_assignments_per_hour` на номер: после порога номер
уходит в конец очереди, даже если формально свободен.

`round_robin` — строгий цикл по списку; `random` — равномерный случайный выбор.
Стратегия задаётся на арендатора или глобально.

### 13.3. Здоровье шлюза

- «Онлайн» — был обмен за `offline_after` (по умолчанию 90 с; для интервала 5 с это
  с запасом).
- Офлайн-номера не назначаются; существующие заявки не продлеваются.
- Если все номера офлайн/заполнены — `503 no_gateway_available`; арендатор должен
  иметь фолбэк (свой SMS-провайдер, другой метод).
- Метрики: `gateway_last_seen_seconds`, `gateway_numbers_active`,
  `pool_available_numbers`.

### 13.4. Разделение арендаторов

Один номер — ровно один арендатор. Валидатор конфигурации запрещает пересечение
пулов. Это даёт однозначную маршрутизацию: событие на номере N обрабатывается только
в заявках арендатора N. Совместное использование номера несколькими арендаторами
не поддерживается в v1 (потребовало бы кода в SMS и сложной изоляции).

### 13.5. Несколько активных заявок на номер шлюза

Номер шлюза — не «один код за раз», а канал с несколькими параллельными заявками:

- до `max_pending_per_number` активных заявок на номер;
- SMS-заявки различаются кодом; код уникален среди активных SMS-заявок этого номера;
- `phone_first` и `code_first` могут висеть одновременно;
- один телефон пользователя может иметь несколько SMS-заявок (лимит
  `max_active_sms_per_phone`), если коды разные;
- `call`/`any` — не более одной активной заявки на пару «телефон + номер шлюза»,
  иначе входящий звонок нельзя однозначно сопоставить.

Матчинг SMS:

```
найти pending-заявки
  where gateway_number = N
    and code_hash = hash(код)
    and expires_at > now
если ровно одна -> verified
если ноль       -> unmatched
если больше одной -> ambiguous (не подтверждать)
```

Матчинг звонка:

```
найти pending call/any-заявки
  where gateway_number = N
    and phone_e164 = номер звонящего
    and expires_at > now
если ровно одна -> verified
иначе           -> unmatched/ambiguous
```

Ограничение по звонку защищено уникальным частичным индексом; SMS-коды — отдельным
уникальным индексом `(gateway_number, code_hash)`. Перед созданием заявки истёкшие
`pending` помечаются `expired`, чтобы они не занимали код и не блокировали звонок.

## 14. Безопасность

### 14.1. Модель угроз

| Угроза | Мера |
|---|---|
| Подбор номера/кода | Лимиты на телефон, IP, арендатора; `phone_first` — 6 цифр/3 попытки/TTL 5 мин; `code_first` — 8 символов/TTL 10 мин |
| Перебор заявок через API | API-ключ арендатора, rate limit, отсутствие информации о чужих номерах |
| Подделка звонящего (Caller ID spoofing) | Не полагаться только на звонок для чувствительных действий; предлагать SMS; риск-сигналы арендатора |
| Утечка токена шлюза | TLS, ротация, IP allowlist, отключение, аномалии (номер не из пула) |
| Повтор запроса обмена | `sync_id` + дедупликация + уникальный индекс |
| Подделка вебхука | HMAC-SHA256, timestamp, allowlist URL |
| SQL-инъекция | Только параметризованные запросы; сортировки — из белого списка |
| XSS в админ-API/будущем UI | Экранирование, `Content-Type`, CSP |
| SSRF через вебхук | URL только из конфигурации, блок private IP, без редиректов |
| DoS | Лимиты тела/соединений, таймауты, rate limit, `Retry-After` |
| Утечка PII в логи | Маскирование телефонов, запрет текстов SMS и кодов |
| Компрометация БД | Шифрование диска, доступ по ролям, retention, аудит |

### 14.2. Валидация входа

- Телефоны: `libphonenumber` (или собственная строгая нормализация), E.164, длина 8–15
  цифр; для РФ `8XXXXXXXXXX` → `+7XXXXXXXXXX`; отклонять добавочные, буквы, эмодзи.
- Страна/префикс: белый список на арендатора (`allowed_countries: [RU]`), запрет
  премиум-номеров.
- JSON: лимит размера, глубины и количества элементов; строки — лимит длины;
  неизвестные поля в API арендатора — `400`; в протоколе шлюза — игнорировать.
- Время: RFC 3339; проверка `|event_time - now| ≤ clock_skew` для матчинга.
- Заголовки: `Content-Type`, `Authorization`; отклонять управляющие символы.
- Никаких `eval`, shell, шаблонов из пользовательских данных.

### 14.3. Аутентификация арендатора

Базовая: `Authorization: Bearer <key>`, ключ 32+ байта, сравнение constant-time,
хранение SHA-256.

Опционально (рекомендуется для production): HMAC-подпись запроса:

```
X-PhoneGate-Timestamp: 1761048000
X-PhoneGate-Signature: v1=hex(hmac_sha256(secret,
    timestamp + "\n" + method + "\n" + request_uri + "\n" + sha256(body)))
```

`request_uri` — путь с query-строкой, как он пришёл на сервер (без хоста).

Проверка: `|now - timestamp| ≤ 300 с`, подпись constant-time, тело не изменено.
При включённом HMAC заголовок `X-PhoneGate-Nonce` обязателен; пара timestamp+nonce
не принимается повторно в течение 10 минут.

### 14.4. Аутентификация шлюза

- Токен в `Authorization: Bearer`; сравнение хэша constant-time.
- Опционально IP allowlist на шлюз (мобильные IP меняются — по умолчанию выключено).
- TLS обязателен для публичного интернета; в приватной сети допустим HTTP, но
  рекомендуется VPN/туннель.
- HMAC для тела запроса — в будущей версии приложения; в v1 токен + TLS.
- Отключение шлюза администратором действует немедленно (проверка на каждом запросе).

### 14.5. Защита от перебора и фрода

- `POST /verifications`: 5 запросов/час на телефон, 60/час на IP, 600/мин на арендатора
  (значения настраиваются).
- Повторный `call`/`any` на ту же пару «телефон + номер шлюза» в пределах TTL — `409`,
  а не новая заявка. SMS-заявок можно несколько: до `max_active_sms_per_phone` на
  телефон; `409` для SMS — только конфликт `Idempotency-Key`.
- Коды: `crypto/rand`, 6 цифр, сравнение constant-time, хэш в БД; код уникален среди
  активных SMS-заявок номера шлюза, при коллизии генерируется заново.
- После 3 неверных кодов — `failed`; новая заявка не раньше чем через 10 минут.
- `code_first`: код 8 символов из 32 (≈40 бит), уникален среди активных SMS-заявок
  на том же номере шлюза, одноразовый, TTL ≤ 15 минут; привязка к номеру шлюза и
  арендатору. Код показывается
  только в личном чате бота и не пишется в логи. SMS с неверным кодом — `unmatched`;
  лимит на отправителя и номер шлюза.
- В `code_first` номер телефона появляется только после SMS; до этого в ответах API
  `phone=null`. Бот обязан сверить `metadata.telegram_user_id` с тем, кому выдан код.
- События без заявки сохраняются как `unmatched` и не влияют на статусы.
- Публичные `/v/{token}` и `/v/{token}/qr.png`: HMAC-токен с TTL заявки, rate limit
  на IP и токен (60/мин), `no-store`, `no-referrer`; в access-логах токен маскируется.
  Ссылка — bearer-секрет: кто её получил, может увидеть код и отправить SMS.
- Аномалии: много событий с одного номера, события вне окна, звонки с скрытого номера —
  метрики и WARN; при необходимости — блокировка номера/шлюза.
- Арендатору рекомендуется CAPTCHA/риск-анализ на своей стороне: телефонная
  авторизация — не единственный фактор для платежей и смены пароля.

### 14.6. Приватность и право

- Телефон и `telegram_user_id` — персональные данные; хранить минимум, ограничивать
  доступ, удалять по TTL. Для бота — отдельная политика конфиденциальности.
- Запись разговоров и тексты SMS — только с согласия и по закону; для авторизации
  запись **не включается**.
- 152-ФЗ (РФ) и аналогичные режимы: определить оператора ПДн, основание обработки,
  место хранения, срок, порядок удаления; при необходимости — согласие в оферте.
- Логи — тоже ПДн: маскировать, ограничить срок, не отправлять в сторонние сервисы
  без договора.
- Токены `page_url`/`qr_url` — не ПДн, но дают доступ к заявке и коду; считать их
  секретом, не логировать, не передавать в аналитику и не использовать в referrer.
- Экспорт и удаление по запросу субъекта — через админ-API (в v1 — ручная процедура).

## 15. Логи и наблюдаемость

### 15.1. Формат

stdout, JSON Lines, UTC, без цветов. Примеры:

```json
{"ts":"2026-10-21T12:00:00.123Z","level":"info","msg":"verification.created","request_id":"req_01J...","tenant":"shop","verification_id":"vrf_01J...","method":"sms","phone":"+7900***4567","gateway_number":"+7900***0001","ttl_s":300}
{"ts":"2026-10-21T12:01:17.456Z","level":"info","msg":"verification.verified","tenant":"shop","verification_id":"vrf_01J...","event":"sms","latency_ms":7733}
{"ts":"2026-10-21T12:01:18.001Z","level":"warn","msg":"gateway.number_unregistered","gateway":"gw_01J...","number":"+7900***0003"}
{"ts":"2026-10-21T12:02:00.000Z","level":"error","msg":"webhook.failed","tenant":"shop","delivery_id":"whd_01J...","attempt":3,"status":502,"error":"bad gateway"}
```

### 15.2. Что логируется

- Каждый HTTP-запрос: `request_id`, метод, путь, статус, длительность, арендатор/шлюз,
  IP (можно маскировать), размер.
- Создание/смена статуса заявки, матчинг, истечение, отмена.
- Регистрация номера, отключение шлюза, ошибки конфигурации.
- Доставка вебхуков: попытка, статус, ошибка (без тела).
- Ошибки БД/паники — со стеком, без секретов.
- Не логируются: токены, API-ключи, коды, полные тексты SMS, тело вебхука,
  `metadata` целиком, токены `page_url`/`qr_url`. В пути `/v/{token}` маскируется
  средняя часть токена; query-строки публичных страниц не логируются.
- Исключение для отладки шлюза: при `logging.log_gateway_payload: true` сырой JSON
  запроса `/exchange` пишется в лог (номера, текст SMS, время). По умолчанию
  выключено; в production включать нельзя. События с номером, не прошедшим E.164,
  логируются с полем `raw_phone`, чтобы было видно, что именно прислало приложение;
  при `gateway.validate_peer_numbers: false` они сохраняются в журнал, но не
  матчатся с заявками.

Уровни: `debug` (детали матчинга), `info` (события), `warn` (подозрительное),
`error` (сбои). Управление через `LOG_LEVEL`/конфиг.

### 15.3. Метрики

- `phonegate_http_requests_total{route,status}`
- `phonegate_http_request_duration_seconds`
- `phonegate_verifications_total{tenant,status,method}`
- `phonegate_verification_match_seconds` (гистограмма)
- `phonegate_gateway_last_seen_seconds{gateway}`
- `phonegate_pool_available_numbers{pool}`
- `phonegate_inbound_events_total{kind,result}`
- `phonegate_webhook_deliveries_total{status}`
- `phonegate_db_errors_total`
- `phonegate_rate_limited_total{scope}`
- `phonegate_public_page_requests_total{kind,status}` (kind: page/status/qr)
- `phonegate_link_errors_total{reason}` (expired/signature/not_found)

### 15.4. Трассировка

- `X-Request-Id` из запроса или сгенерированный; возвращается клиенту.
- Для события шлюза — `gateway_id` + `sync_id` в логах, чтобы связать обмен и матчинг.
- OpenTelemetry — опционально, не обязателен для v1.

## 16. Развёртывание

### 16.1. Бинарник

```bash
CGO_ENABLED=0 go build -trimpath -ldflags "-s -w" -o phonegate-server ./cmd/server
./phonegate-server -config /etc/phonegate/config.yaml
```

Флаги: `-config`, `-check` (проверить конфигурацию и выйти), `-version`.
Сигналы: `SIGTERM` — graceful shutdown (30 с), `SIGHUP` — reload.

### 16.2. Docker

```dockerfile
FROM gcr.io/distroless/static-debian12:nonroot
COPY phonegate-server /phonegate-server
USER nonroot:nonroot
VOLUME ["/data"]
EXPOSE 8080
ENTRYPOINT ["/phonegate-server", "-config", "/etc/phonegate/config.yaml"]
```

```bash
docker run -d --name phonegate \
  -p 8080:8080 \
  -v phonegate-data:/data \
  -v $PWD/config.yaml:/etc/phonegate/config.yaml:ro \
  -e SHOP_API_KEY_SHA256=... \
  -e SHOP_WEBHOOK_SECRET=... \
  -e LINKS_SECRET=... \
  ghcr.io/example/phonegate-server:1.0
```

Требования: запуск от non-root, read-only root FS (кроме `/data` и `/tmp`),
`no-new-privileges`, лимиты CPU/памяти, healthcheck на `/healthz`.
Образ ~15–25 МБ; для SQLite внешние сервисы не нужны.

### 16.3. Linux/systemd

```ini
[Unit]
Description=PhoneGate backend
After=network-online.target
Wants=network-online.target

[Service]
User=phonegate
Group=phonegate
StateDirectory=phonegate
ExecStart=/usr/local/bin/phonegate-server -config /etc/phonegate/config.yaml
Restart=on-failure
RestartSec=3
NoNewPrivileges=true
ProtectSystem=strict
ProtectHome=true
PrivateTmp=true
ReadWritePaths=/var/lib/phonegate
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target
```

TLS — на reverse proxy (Caddy/Nginx) или встроенный (опционально). Прокси должен
передавать `X-Forwarded-For` только от доверенного источника; бэкенд доверяет ему
лишь при `trusted_proxies`. Публичные `/v/` должны быть доступны без API-ключа;
прокси не должен кэшировать их ответы (`Cache-Control: no-store`) и логировать
полный токен ссылки.

### 16.4. Часы и сеть

- NTP обязателен: от времени зависят TTL, HMAC и окна матчинга.
- `clock_skew` по умолчанию 120 с; при большем расхождении — WARN.
- Исходящие соединения: только к вебхукам арендаторов (allowlist) и БД.

| Параметр | Цель |
|---|---|
| API p95 | < 100 мс (без вебхука) |
| Матчинг события | < 50 мс |

## 18. Тестирование

### 18.1. Модульные

- Нормализация телефонов (РФ, международные, мусор).
- Генерация/сравнение кодов, constant-time.
- Дедупликация событий.
- Выбор номера: least_loaded, ротация, sticky, офлайн, переполнение.
- Валидация конфигурации: пересечение пулов, слабые секреты, неизвестные поля.
- Подпись/проверка вебхуков и HMAC.
- Подпись/проверка токена `page_url`/`qr_url`, TTL, подмена, неверный `sid`/код.

### 18.2. Интеграционные

Сценарии с фейковым шлюзом (HTTP-клиент, повторяющий формат приложения):

1. SMS с верным кодом → `verified` + вебхук.
2. SMS с неверным кодом ×3 → `failed`.
3. Звонок `missed` → `verified`.
4. Звонок с чужого номера → `unmatched`.
5. Повтор обмена с тем же `sync_id` → без дублей.
6. Просрочка → `expired` + вебхук.
7. Отмена → `cancelled`.
8. Нет живых номеров → `503`.
9. Вебхук 500 → повторы, затем `failed`; статус доступен опросом.
10. Изоляция арендаторов: событие на номере A не видно арендатору B.
11. Ограничение частоты → `429` + `Retry-After`.
12. Перезапуск с SQLite → заявки и история на месте; с memory — потеряны.
13. `code_first`: заявка без `phone` → SMS с кодом → `verified`, `phone` заполнен.
14. `code_first`: неверный код → `unmatched`, заявка не меняется.
15. `code_first`: повторное использование кода → отклоняется; `phone` в запросе → `400`.
16. `code_first`: SMS на чужой номер шлюза → нет совпадения (заявка не подтверждается).
17. `links` для `sms`: `sms_uri` содержит номер и URL-кодированный код; `tel_uri=null`;
    `qr_url` отдаёт PNG, QR декодируется в `sms_uri` (совместимость);
    `sms_qr_url` отдаёт PNG, QR ведёт на HTTPS-страницу `/go/sms`.
18. `links` для `call`: `sms_uri`/`sms_uri_ios` отсутствуют, `tel_uri` ведёт на номер,
    QR декодируется в `tel_uri` (совместимость); `tel_qr_url` ведёт на `/go/call`.
19. `links` для `any`: есть SMS и звонок; `qr_url` ведёт в SMS (совместимость);
    `sms_qr_url` и `tel_qr_url` — разные QR-коды для каждого действия.
20. `page_url`: страница открывается, показывает кнопки и маскированный телефон;
    подпись/токен проверяются, истёкший токен → `410`, испорченный → `404`.
21. `GET /verifications/{id}` не содержит `links` и `code`; ссылки из старого ответа
    после `retry` не подтверждают новую заявку.

### 18.3. Безопасность

- Фаззинг JSON и полей телефона.
- SQL-инъекции в фильтрах админ-API.
- Replay HMAC, подмена тела, просроченный timestamp.
- SSRF: вебхук на `127.0.0.1`, `169.254.169.254`, private range.
- Огромное тело, глубокая вложенность, медленная отправка (slowloris).
- Брутфорс кода и номера.
- Подмена/просрочка токена страницы и QR, rate limit публичных `/v/`, отсутствие
  токена в логах и Referer.

### 18.4. E2E

- Реальное приложение PhoneGate + эмулятор/телефон + тестовый бэкенд.
- Проверка задержки: интервал 5 с, звонок/SMS, время до `verified`.
- Проверка, что бэкенд не выдаёт команды и приложение ничего не отправляет.
- Проверка ссылок и QR на iPhone Safari, Android Chrome и Telegram WebView:
  SMS с подставленным кодом, звонок, копирование, десктопный QR.

## 19. Ограничения и риски

| Риск | Влияние | Смягчение |
|---|---|---|
| Caller ID можно подделать | Ложная авторизация по звонку | SMS как основной метод; риск-анализ арендатора; не использовать для платежей |
| Утечка кода code-first / социнженерия | Чужой номер привязывается к аккаунту | Личный чат, TTL, одноразовость, подтверждение номера, не использовать для платежей |
| Пересылка ссылки/QR | Другой человек видит код или завершает заявку | Короткий TTL, bearer-токен, сверка `telegram_user_id`, подтверждение номера, не логировать ссылку |
| Telegram WebView блокирует `sms:`/`tel:` | Пользователь не может открыть SMS/звонок | HTTPS-страница с кнопками, копирование, «Открыть в браузере», QR на десктопе |
| iOS не подставляет текст SMS | Пользователь вводит код вручную | `sms_uri_ios`, кнопка копирования, короткий код; проверять на реальных клиентах |
| QR-сканер не понимает `sms:`/`tel:` | QR бесполезен | На странице есть номер, код и кнопки; QR — дополнительный путь |
| Задержка опроса шлюза | Авторизация 5–60 с | В v1 — интервал 5 с для auth-шлюзов; long-poll/WebSocket после v1 |
| Android не отдаёт номер SIM | Неверная привязка событий | Ручной ввод + подтверждение в админке; доработка приложения |
| SMS может не дойти | Заявка истекает | TTL, повтор, альтернативный звонок, фолбэк арендатора |
| Оператор блокирует номера за спам | Пул деградирует | Ротация, лимиты, мониторинг, замена SIM |
| Шлюз офлайн | Нет авторизации | Health-check, 503, фолбэк, уведомление оператора |
| Утечка БД | PII и история | Шифрование диска, минимум данных, retention, доступ |
| Юридические требования | Штрафы/блокировка | 152-ФЗ, согласия, договор с арендаторами, аудит |
| Мошенничество арендатора | Спам/жалобы | Договор, лимиты, блокировка, аудит |

## 20. Другие применения приложения-шлюза

Авторизация — не единственный сценарий. Тот же бэкенд (приём событий + API + история)
подходит для:

1. **SMS/звонки для QA и тестовых сред.** Разработчики получают номер и читают
   входящие коды через API. Ближайший продукт к авторизации, переиспользует 90% кода.
2. **Корпоративный архив связи.** Сбор SMS и журнала звонков с нескольких телефонов,
   поиск, экспорт, срок хранения. Востребовано в малом бизнесе и для разборов.
3. **Пропущенные звонки → задача в CRM.** Входящий/пропущенный вызов создаёт лид,
   менеджер перезванивает. Сам обратный звонок — отдельная платная функция.
4. **Голосовые опросы и автоответчик.** Приложение уже проигрывает mp3 и записывает
   ответ; бэкенд собирает записи и оценки (NPS, опросы).
5. **Подтверждение согласия.** Пользователь звонит на номер, разговор записывается
   с согласия; бэкенд хранит хэш, время и запись как доказательство.
6. **Мониторинг и алерты.** Входящие SMS от устройств/систем парсятся и пересылаются
   в Telegram/Slack/почту; шлюз как резервный канал.
7. **IoT-телеметрия по SMS.** Устройства без интернета шлют SMS; бэкенд разбирает
   формат и складывает в БД.
8. **Антиспам/репутация номеров.** Анализ входящих звонков и SMS, жалобы, чёрные
   списки (осторожно с приватностью и ложными срабатываниями).
9. **Атрибуция офлайн-рекламы.** «Позвоните на номер X» — по номеру шлюза считаем
   отклик кампании; звонки и SMS попадают в аналитику.
10. **Пул номеров для маркетплейсов.** Каждый арендатор получает свои номера для
    входящей связи; разделение и история уже есть в архитектуре.
11. **Привязка номера в Telegram-боте.** Бот не знает номер; пользователь отправляет
    SMS с кодом, PhoneGate возвращает номер отправителя. Отдельный сценарий
    `code_first` — [telegram.md](telegram.md).

Наиболее близкий к текущему ТЗ продукт — **«входящие SMS/звонки как API»** (пункт 1):
он не требует исходящих затрат, использует тот же приём событий и может быть
белым лейблом для авторизации. Его стоит рассмотреть как второй тариф.

## 22. Открытые вопросы

1. Язык и стек: предполагается Go; есть ли требования к другому?
2. Домен, TLS, хостинг: свой сервер, VPS, облако? Нужен ли встроенный Let's Encrypt?
3. Сколько арендаторов, шлюзов и заявок в день ожидается на старте?
4. Основной метод: SMS, звонок или оба? Допустим ли пропущенный вызов?
5. Публичный домен и TLS для страницы подтверждения: какой URL, нужен ли брендинг
