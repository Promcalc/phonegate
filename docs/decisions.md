# Журнал решений

Формат: `D<номер>` — решение, причина, следствия. Новые решения добавляются в конец,
нумерация не меняется. Решения по ходу этапов — в разделе «По этапам».

## Общие решения

### D1. AGP 9 с built-in Kotlin
Принято на M1. AGP 9.1.1 включает встроенную поддержку Kotlin и сам регистрирует расширение
`kotlin`; применение `org.jetbrains.kotlin.android` приводит к ошибке
«Cannot add extension with name 'kotlin'». В сборке оставлены только плагины
`com.android.application`, `org.jetbrains.kotlin.plugin.compose` и
`org.jetbrains.kotlin.plugin.serialization`. Версия KGP (2.2.10) приходит транзитивно из AGP,
`jvmTarget` берётся из `compileOptions.targetCompatibility`, отдельный блок `kotlin {}` не нужен.
Следствие: `android.builtInKotlin=false` не выставляем, откат не планируется.

### D2. targetSdk = 33
Принято перед M1. На targetSdk 34+ Android запрещает старт foreground-службы с типом
`microphone` из фона, а на targetSdk 35+ ещё и запрещает старт `dataSync`-службы из
`BOOT_COMPLETED` и ограничивает `dataSync` шестью часами в сутки. Нам нужны и автостарт, и
микрофон в фоне, поэтому берём 33. Приложение ставится сайдлоадом, требований Google Play нет.
Следствие: тип службы объявляем явно (`dataSync|microphone`), разрешения `FOREGROUND_SERVICE_*`
прописаны — это даёт доступ к микрофону в фоне. Если прошивка всё равно откажет в старте,
включается план Б: уведомление «откройте приложение» и повышение targetSdk.

### D3. Автоответ — `acceptRingingCall()` с фолбэком на роль диалера
Публичного API «снять трубку» для приложения без роли диалера не существует. Порядок попыток:
`TelecomManager.acceptRingingCall()` (разрешение `ANSWER_PHONE_CALLS`) → при неудаче предложить
пользователю роль «Телефон по умолчанию» и работать через `InCallService`. Логика спрятана за
интерфейсом `CallController`, поэтому фолбэк не затрагивает бизнес-логику.

### D4. Голос абоненту — через громкую связь и микрофон
Подмешать аудио в линию передачи публичными средствами нельзя. Включаем громкую связь,
проигрываем mp3 — абонент слышит его через микрофон. Качество ниже студийного, есть лёгкий эх.
Принято сознательно, как единственный вариант без root/системных прав.

### D5. Запись ответа абонента — `MediaRecorder` с источником `MIC`
`VOICE_CALL` для обычных приложений закрыт с Android 10. Пишем то, что слышит микрофон, при
включённой громкой связи. Требуется `RECORD_AUDIO` и запущенная служба с типом `microphone`
(см. D2). Если модем держит микрофон, `MediaRecorder.start()` может упасть или дать тишину —
ошибка пишется в лог, звонок корректно завершается.

### D6. В отчёт идут только новые SMS и звонки
Формулировка ТЗ «список всех СМС» трактуется как «все новые с момента предыдущей отправки»,
иначе каждый цикл повторно отправлял бы всю историю. Курсор по `_id` и времени хранится
в настройках и переживает перезагрузку.

### D7. UI на Compose
Настройки и логи — Kotlin + Jetpack Compose (Material 3), две вкладки в одной Activity
(`MainActivity`), без navigation-compose: переключение вкладок — обычное состояние Compose.

### D8. Авторизация — два поля
`authHeaderName` (по умолчанию `Authorization`) и `authToken`. Если имя заголовка пустое,
заголовок не добавляется вовсе. Значение подставляется как есть (например `Bearer abc123`).

### D9. mp3 выбирается через SAF
Пути вида `/storage/...` на Android 14–16 без разрешений недоступны. Файл выбирается через
`ACTION_OPEN_DOCUMENT`, хранится persistable-URI, в интерфейсе показывается читаемый путь.
Если файл удалён или URI отозван — в лог WARN, поведение как «файла нет» (звонок сбрасывается).

### D10. Записи разговоров — N последних
Хранится `keepRecordings` (по умолчанию 20) самых свежих файлов в `files/records`, остальные
удаляются после каждого обработанного звонка.

### D11. POST отправляется в каждом цикле
Даже если новых SMS и звонков нет, POST уходит (пустые массивы) — сервер видит, что устройство
живо.

### D12. Ошибки — копим, курсор только при успехе
Любая ошибка (сеть, таймаут, 4xx, 5xx) оставляет данные неотправленными, следующий цикл
отправляет накопленное окно целиком. Чтобы можно было вручную сдвинуть точку начала, в
настройках есть поле «Начало сбора данных»: при его изменении сбрасываются `lastSmsId`,
`lastCallId` и точка отсчёта. Поле `sync_id` (UUID окна) добавляется в запрос, чтобы сервер мог
распознать повторную отправку того же окна.

### D13. Все типы звонков + `direction`
В отчёт идут входящие, пропущенные и исходящие звонки, с полем `direction` = `in|out|missed`.
Маппинг `CallLog.Calls.TYPE`: `INCOMING`/`ANSWERED_EXTERNALLY`/`VOICEMAIL` → `in`,
`OUTGOING` → `out`, `MISSED`/`REJECTED`/`BLOCKED` → `missed`. Ответ сервера поле не использует.

### D14. Два адреса
1. **URL обмена** — из ТЗ: отправляем принятые SMS и журнал звонков, в ответ получаем SMS и
   звонки к исполнению.
2. **URL отчёта об исходящих** — отправляем то, что сделали сами (отправленные SMS и
   совершённые звонки). Пустой адрес — отчёт не отправляется. Обрабатывается независимо от
   первого URL, со своим курсором.

Звонки, которые совершает само приложение, попадают и в первый отчёт (там весь журнал), и во
второй; сервер может отфильтровать их по `direction = "out"`.

### D15. Ожидание по звонкам — в секундах
Событие «гудок» платформа не отдаёт (на звонок приходит одно состояние `RINGING`), поэтому
настройки задаются в секундах. Формулировка про «количество сигналов» в ТЗ допускает такой
вариант.

### D16. applicationId `ru.promcalc.phonegate`
Namespace, applicationId, каталоги исходников и тестов переименованы на M1.

## По этапам

### M1 — каркас
- Создана структура пакетов `ru/promcalc/phonegate`, `MainActivity` с двумя вкладками,
  заглушки экранов настроек и логов.
- Манифест: полный список разрешений и `usesCleartextTraffic="true"` объявлены заранее;
  служба и приёмники будут добавлены на этапах M5–M7.
- Тема приложения переведена на `Theme.Material3.DayNight.NoActionBar`.
- Сборка `:app:assembleDebug` проходит (проверено локально, AGP 9.1.1 + Kotlin 2.2.10 + Compose
  BOM 2024.09.00).
- Версии зависимостей подобраны под эпоху Kotlin 2.2.10, чтобы не ловить несовместимость
  Compose-компилятора с рантаймом.

### M2 — настройки
- `Settings`, `SettingsRepository` (SharedPreferences + `StateFlow`) и `SyncStateStore`
  (курсоры обмена и отчёта). Первый запуск фиксирует «Начало сбора данных» текущим моментом.
- Экран настроек: все поля из плана, системные диалоги выбора даты и времени, выбор mp3 через
  SAF с закреплением доступа, проверка значений перед сохранением.
- Изменение «Начала сбора данных» сбрасывает курсоры (D12) и показывает об этом сообщение.
- `core/Time.kt` — формат с оффсетом на `Calendar` (без desugaring при minSdk 24).
  Тесты нашли ошибку в номере группы регулярного выражения при разборе зоны — исправлено,
  9 тестов времени проходят.
- Отступление от плана: юнит-тесты на время написаны на M2, а не на M8 — логика чистая,
  а цена ошибки в ней высокая (это же поле уходит на сервер).
- Кнопка запуска/остановки фонового процесса сознательно не сделана на M2: она появится
  вместе со службой на M5, чтобы не показывать кнопку без действия.

### M3 — логи
- Формат файла — JSONL (`files/logs/gateway-ГГГГ-ММ-ДД.jsonl`), по объекту `LogEntry` на строку:
  читается глазами и без потерь восстанавливается в память после перезапуска (в буфер
  подгружаются последние 300 записей последнего файла).
- Кольцевой буфер на 1000 записей в памяти отдаётся в UI как `StateFlow`; запись в файл идёт
  в отдельном потоке, логирование не блокирует службу.
- Файлы старше 7 дней удаляются при старте репозитория.
- Категории записи (`SERVICE`, `HTTP`, `SMS`, `CALL_IN`, `CALL_OUT`) сразу сделаны под фильтр
  на экране логов: чипы категорий, поиск по сообщению и подробностям, копирование в буфер,
  очистка с подтверждением, разворачивание подробностей (JSON запроса/ответа).
- Отдельного фасада `AppLogger` из плана не завели: репозиторий доступен как
  `context.logRepository`, дополнительные обёртки были бы лишним слоем.
