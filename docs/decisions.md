# Журнал решений

Формат: `D<номер>` — решение, причина, следствия. Новые решения добавляются в конец,
нумерация не меняется. Решения по ходу этапов — в разделе «По этапам».

## Общие решения

### D1. AGP 9 с built-in Kotlin
Принято на M1. AGP 9.1.1 включает встроенную поддержку Kotlin и сам регистрирует расширение
`kotlin`; применение `org.jetbrains.kotlin.android` приводит к ошибке
«Cannot add extension with name 'kotlin'». В сборке оставлены только плагины
`com.android.application`, `org.jetbrains.kotlin.plugin.compose` и
`org.jetbrains.kotlin.plugin.serialization`. Версия KGP (2.2.10) приходит транзитивно из AGP,
`jvmTarget` берётся из `compileOptions.targetCompatibility`, отдельный блок `kotlin {}` не нужен.
Следствие: `android.builtInKotlin=false` не выставляем, откат не планируется.

### D2. targetSdk = 33
Принято перед M1. На targetSdk 34+ Android запрещает старт foreground-службы с типом
`microphone` из фона, а на targetSdk 35+ ещё и запрещает старт `dataSync`-службы из
`BOOT_COMPLETED` и ограничивает `dataSync` шестью часами в сутки. Нам нужны и автостарт, и
микрофон в фоне, поэтому берём 33. Приложение ставится сайдлоадом, требований Google Play нет.
Следствие: тип службы объявляем явно (`dataSync|microphone`), разрешения `FOREGROUND_SERVICE_*`
прописаны — это даёт доступ к микрофону в фоне. Если прошивка всё равно откажет в старте,
включается план Б: уведомление «откройте приложение» и повышение targetSdk.

### D3. Автоответ — `acceptRingingCall()` с фолбэком на роль диалера
Публичного API «снять трубку» для приложения без роли диалера не существует. Порядок попыток:
`TelecomManager.acceptRingingCall()` (разрешение `ANSWER_PHONE_CALLS`) → при неудаче предложить
пользователю роль «Телефон по умолчанию» и работать через `InCallService`. Логика спрятана за
интерфейсом `CallController`, поэтому фолбэк не затрагивает бизнес-логику.

### D4. Голос абоненту — через громкую связь и микрофон
Подмешать аудио в линию передачи публичными средствами нельзя. Включаем громкую связь,
проигрываем mp3 — абонент слышит его через микрофон. Качество ниже студийного, есть лёгкий эх.
Принято сознательно, как единственный вариант без root/системных прав.

### D5. Запись ответа абонента — `MediaRecorder` с источником `MIC`
`VOICE_CALL` для обычных приложений закрыт с Android 10. Пишем то, что слышит микрофон, при
включённой громкой связи. Требуется `RECORD_AUDIO` и запущенная служба с типом `microphone`
(см. D2). Если модем держит микрофон, `MediaRecorder.start()` может упасть или дать тишину —
ошибка пишется в лог, звонок корректно завершается.

### D6. В отчёт идут только новые SMS и звонки
Формулировка ТЗ «список всех СМС» трактуется как «все новые с момента предыдущей отправки»,
иначе каждый цикл повторно отправлял бы всю историю. Курсор по `_id` и времени хранится
в настройках и переживает перезагрузку.

### D7. UI на Compose
Настройки и логи — Kotlin + Jetpack Compose (Material 3), две вкладки в одной Activity
(`MainActivity`), без navigation-compose: переключение вкладок — обычное состояние Compose.

### D8. Авторизация — два поля
`authHeaderName` (по умолчанию `Authorization`) и `authToken`. Если имя заголовка пустое,
заголовок не добавляется вовсе. Значение подставляется как есть (например `Bearer abc123`).

### D9. mp3 выбирается через SAF
Пути вида `/storage/...` на Android 14–16 без разрешений недоступны. Файл выбирается через
`ACTION_OPEN_DOCUMENT`, хранится persistable-URI, в интерфейсе показывается читаемый путь.
Если файл удалён или URI отозван — в лог WARN, поведение как «файла нет» (звонок сбрасывается).

### D10. Записи разговоров — N последних
Хранится `keepRecordings` (по умолчанию 20) самых свежих файлов в `files/records`, остальные
удаляются после каждого обработанного звонка.

### D11. POST отправляется в каждом цикле
Даже если новых SMS и звонков нет, POST уходит (пустые массивы) — сервер видит, что устройство
живо.

### D12. Ошибки — копим, курсор только при успехе
Любая ошибка (сеть, таймаут, 4xx, 5xx) оставляет данные неотправленными, следующий цикл
отправляет накопленное окно целиком. Чтобы можно было вручную сдвинуть точку начала, в
настройках есть поле «Начало сбора данных»: при его изменении сбрасываются `lastSmsId`,
`lastCallId` и точка отсчёта. Поле `sync_id` (UUID окна) добавляется в запрос, чтобы сервер мог
распознать повторную отправку того же окна.

### D13. Все типы звонков + `direction`
В отчёт идут входящие, пропущенные и исходящие звонки, с полем `direction` = `in|out|missed`.
Маппинг `CallLog.Calls.TYPE`: `INCOMING`/`ANSWERED_EXTERNALLY`/`VOICEMAIL` → `in`,
`OUTGOING` → `out`, `MISSED`/`REJECTED`/`BLOCKED` → `missed`. Ответ сервера поле не использует.

### D14. Два адреса
1. **URL обмена** — из ТЗ: отправляем принятые SMS и журнал звонков, в ответ получаем SMS и
   звонки к исполнению.
2. **URL отчёта об исходящих** — отправляем то, что сделали сами (отправленные SMS и
   совершённые звонки). Пустой адрес — отчёт не отправляется. Обрабатывается независимо от
   первого URL, со своим курсором.

Звонки, которые совершает само приложение, попадают и в первый отчёт (там весь журнал), и во
второй; сервер может отфильтровать их по `direction = "out"`.

### D15. Ожидание по звонкам — в секундах
Событие «гудок» платформа не отдаёт (на звонок приходит одно состояние `RINGING`), поэтому
настройки задаются в секундах. Формулировка про «количество сигналов» в ТЗ допускает такой
вариант.

### D16. applicationId `ru.promcalc.phonegate`
Namespace, applicationId, каталоги исходников и тестов переименованы на M1.

## По этапам

### M1 — каркас
- Создана структура пакетов `ru/promcalc/phonegate`, `MainActivity` с двумя вкладками,
  заглушки экранов настроек и логов.
- Манифест: полный список разрешений и `usesCleartextTraffic="true"` объявлены заранее;
  служба и приёмники будут добавлены на этапах M5–M7.
- Тема приложения переведена на `Theme.Material3.DayNight.NoActionBar`.
- Сборка `:app:assembleDebug` проходит (проверено локально, AGP 9.1.1 + Kotlin 2.2.10 + Compose
  BOM 2024.09.00).
- Версии зависимостей подобраны под эпоху Kotlin 2.2.10, чтобы не ловить несовместимость
  Compose-компилятора с рантаймом.

### M2 — настройки
- `Settings`, `SettingsRepository` (SharedPreferences + `StateFlow`) и `SyncStateStore`
  (курсоры обмена и отчёта). Первый запуск фиксирует «Начало сбора данных» текущим моментом.
- Экран настроек: все поля из плана, системные диалоги выбора даты и времени, выбор mp3 через
  SAF с закреплением доступа, проверка значений перед сохранением.
- Изменение «Начала сбора данных» сбрасывает курсоры (D12) и показывает об этом сообщение.
- `core/Time.kt` — формат с оффсетом на `Calendar` (без desugaring при minSdk 24).
  Тесты нашли ошибку в номере группы регулярного выражения при разборе зоны — исправлено,
  9 тестов времени проходят.
- Отступление от плана: юнит-тесты на время написаны на M2, а не на M8 — логика чистая,
  а цена ошибки в ней высокая (это же поле уходит на сервер).
- Кнопка запуска/остановки фонового процесса сознательно не сделана на M2: она появится
  вместе со службой на M5, чтобы не показывать кнопку без действия.

### M3 — логи
- Формат файла — JSONL (`files/logs/gateway-ГГГГ-ММ-ДД.jsonl`), по объекту `LogEntry` на строку:
  читается глазами и без потерь восстанавливается в память после перезапуска (в буфер
  подгружаются последние 300 записей последнего файла).
- Кольцевой буфер на 1000 записей в памяти отдаётся в UI как `StateFlow`; запись в файл идёт
  в отдельном потоке, логирование не блокирует службу.
- Файлы старше 7 дней удаляются при старте репозитория.
- Категории записи (`SERVICE`, `HTTP`, `SMS`, `CALL_IN`, `CALL_OUT`) сразу сделаны под фильтр
  на экране логов: чипы категорий, поиск по сообщению и подробностям, копирование в буфер,
  очистка с подтверждением, разворачивание подробностей (JSON запроса/ответа).
- Отдельного фасада `AppLogger` из плана не завели: репозиторий доступен как
  `context.logRepository`, дополнительные обёртки были бы лишним слоем.

### M4 — сбор данных и отправка
- Сбор: `SmsReader` (только входящие попадают в отчёт, но курсор по `_id` двигается по всем
  прочитанным строкам) и `CallLogReader` (все типы звонков, `direction` из типа записи).
  Скрытые колонки `sub_id` / `subscription_id` читаются с откатом на запрос без них: не все
  прошивки их отдают.
- SIM определяется по подписке, а если её в журнале нет — по идентификатору телефонного
  аккаунта (`SIM1`, `SIM2`). Если и это не помогло, запись относится к первой настроенной SIM
  и в лог пишется WARN: терять данные молча хуже, чем показать предупреждение.
- Номера сравниваются в каноническом виде: только цифры, ведущая восьмёрка заменяется семёркой,
  10-значный номер трактуется как номер без кода страны (решение — под российские SIM).
- Ключ отчёта — номер SIM из настроек. Если не задан ни один номер, обмен не выполняется
  (в лог WARN): без ключа структуру из ТЗ не собрать.
- `ReportJson` собирает JSON вручную (`buildJsonObject`), потому что ключи верхнего уровня —
  динамические номера телефонов. Форма отчёта закреплена юнит-тестом со сравнением всего
  дерева JSON с ожидаемым.
- Дубли команд: сервер может повторять команды в каждом ответе, поэтому `TaskStore.addIfAbsent`
  не добавляет задачу с тем же типом, номером, текстом и временем. Задачи лежат в
  `files/tasks.json` и переживают перезагрузку.
- `OutgoingJournal` (`files/outgoing.json`) — собственный журнал выполненных действий; из него
  строится отчёт на второй URL. В отчёт попадают только успешные действия (неудачные попытки
  остаются в журнале и логах), курсор `lastOutgoingRecordId` двигается по всем записям.
- Неизвестный тип звонка из журнала относится к `missed` с WARN: все семь документированных
  типов разобраны явно, а «непонятный звонок» безопаснее показать как несостоявшийся.
- Кнопка «Отправить сейчас» на экране настроек заблокирована, пока есть несохранённые
  изменения: иначе отправка шла бы со старыми настройками.
- Направление `direction` для звонков, совершённых самим приложением, в отчёте об исходящих
  всегда `out`.

### M5 — фоновая служба
- `GatewayService`: `START_STICKY`, постоянное уведомление с кнопкой «Остановить», цикл
  `обмен → пауза`; пауза отсчитывается по часам, поэтому длительный обмен не сдвигает график.
  На время цикла берётся `PARTIAL_WAKE_LOCK` с таймаутом.
- Типы foreground-службы перебираются от `dataSync|microphone` к `dataSync` и затем к пустому:
  если система не принимает микрофонный тип (ограничения Android 11+ на работу в фоне), служба
  всё равно поднимается ради обмена, а причина остаётся в логе. Иначе отказ в одном типе
  означал бы полностью неработающий фон.
- Страховочный будильник (`SyncAlarmScheduler`) — вторая линия обороны для прошивок, которые
  выгружают фон: точный будильник, а если точные запрещены — неточный. Ставится на каждый
  следующий цикл, а также в `onTaskRemoved` (пользователь убрал приложение из списка задач).
- Остановка из уведомления сделана широковещательным приёмником, а не `Intent` в службу:
  запуск службы из фона ограничен, а остановка разрешена всегда.
- `serviceEnabled` — сохранённое намерение «процесс должен работать»; оно же решает вопрос
  автозапуска после перезагрузки (вместе с `startOnBoot`). Если пользователь остановил процесс
  вручную, после включения телефона он не поднимется.
- Переключатель «Запускать при включении телефона» заблокирован, пока процесс остановлен: так
  не возникает состояния «автозапуск включён, а запускать нечего».
- Сохранение настроек перезапускает процесс (требование ТЗ) — цикл сразу работает с новыми
  значениями.
- Отступление от плана: запрос разрешений (`POST_NOTIFICATIONS`), онбординг и исключение из
  оптимизации батареи перенесены на M8 целиком — на M5 важно было получить работающий цикл.
  Без разрешения уведомление просто не показывается, обмен при этом работает.

### M6 — исходящие задачи
- `SmsSender`: отправка через `createForSubscriptionId` (на старых Android —
  `getSmsManagerForSubscriptionId`), длинный текст режется на части. Успех — сообщение
  передано телефонии; отчёт о доставке в первой версии не отслеживается (D15).
- `CallPlacer`: звонок ставится `TelecomManager.placeCall` (API 26+), а не `ACTION_CALL`:
  начиная с Android 10 запуск активити дозвона из фона запрещён, а `placeCall` работает без
  активити. Ниже API 26 — откат на `ACTION_CALL`.
- Завершение звонка — `endCall()` (API 28+). Ниже API 28 программно положить трубку нельзя:
  пишем WARN и оставляем это пользователю.
- Разговор считается состоявшимся, если `isInCall` подтвердил его в течение 45 с; иначе звонок
  помечается «не соединился» с нулевой длительностью. Количество секунд до отбоя берётся из
  настроек и отсчитывается от момента соединения, а не от нажатия «позвонить».
- Аккаунт SIM ищется по идентификатору `SIM1`/`SIM2`, затем по идентификатору подписки, затем
  по порядку — каждый откат сопровождается WARN: молчаливая отправка звонка не с той SIM хуже
  предупреждения.
- Неудачная задача возвращается в очередь (до 3 попыток), потому что причины обычно временные:
  нет сети, идёт другой разговор, не выдано разрешение. После третьей попытки — `FAILED`.
- Проваленные задачи не участвуют в защите от дублей: если сервер пришлёт ту же команду снова,
  появится новая задача, которую можно исполнить после устранения помехи.
- `TaskExecutor` — один на процесс, с флагом занятости: цикл службы и кнопка «Отправить сейчас»
  могут прийти одновременно, а одну задачу нельзя исполнить дважды.
- Ручная отправка после получения команды будит цикл службы через `Channel` — иначе команда с
  наступившим временем ждала бы планового пробуждения до конца интервала.
- Время звонка в отчёте об исходящих — момент начала звонка, а не момент отбоя: иначе
  длительность разговора сдвигала бы отметку времени.

### M7 — входящие звонки
- `IncomingCallWatcher` ставит отдельного слушателя на каждую активную подписку
  (`createForSubscriptionId`), поэтому известно, на какую SIM звонят: от этого зависит, какое
  mp3 проигрывать. На Android 12+ это `TelephonyCallback`, ниже — `PhoneStateListener`.
  Регистрация идёт из `onCreate` службы, то есть из главного потока: `PhoneStateListener`
  требует поток с очередью сообщений, а создание из фонового потока падает.
- Если список подписок недоступен (нет `READ_PHONE_STATE`), слушаем состояние телефона в целом
  и считаем, что звонят на первую SIM, — с предупреждением в лог. Молча подставлять чужое
  сообщение хуже, чем сказать об этом.
- Номер звонящего в логе есть только на Android 11 и ниже: новый колбэк состояния звонка номер
  не отдаёт. Сам номер всё равно уходит на сервер в составе журнала вызовов.
- Сценарий прерывается в любой момент: абонент положил трубку — шаги останавливаются
  (проверка флага между шагами); трубку снял сам пользователь — сценарий отменяется целиком,
  иначе мы бы говорили в уже идущий разговор.
- Громкая связь: на Android 12+ выбирается устройство связи (`setCommunicationDevice`) с громким
  динамиком, ниже — `isSpeakerphoneOn`. Оба публичных способа помечены устаревшими, но замены
  для «просто включить громкую связь» нет.
- Снятие трубки — `acceptRingingCall` (на Android 8+ — перегрузка с типом видео). Весь этот API
  помечен устаревшим в пользу роли «Телефон по умолчанию»; когда роль появится, сценарий
  переедет в `InCallService`, поэтому управление вызовом спрятано за интерфейсом
  `CallController`.
- mp3 перед воспроизведением копируется в `files/message-cache`: играть напрямую из документа
  выбранного провайдера ненадёжно. Копия обновляется при смене файла в настройках.
- Запись ответа: `m4a`/AAC, 16 кГц, моно, источник микрофона перебирается
  (`MIC` → `VOICE_RECOGNITION` → `DEFAULT`) — вариант из плана рисков. Пустая запись удаляется,
  а не остаётся мусором в файлах.
- Записи лежат в `files/records/rec-<дата>-sim<N>.m4a`; после каждой записи лишние файлы
  удаляются по настройке «хранить записей разговора». Отдельного экрана для прослушивания
  записей пока нет — это отложено на M8.
- Нет mp3 или файл недоступен — звонок сбрасывается (`endCall`), как требует ТЗ. На Android 8
  и ниже сбросить звонок нельзя: пишем предупреждение, звонок остаётся неотвеченным.

### M8 — доступы, записи, релиз- Отдельная вкладка «Доступ»: список разрешений со статусом, одна кнопка на все недостающие
  запросы и переходы в системные настройки для особых доступов (исключение из оптимизации
  батареи, точные будильники). Состояние перечитывается при возвращении в окно: системные
  настройки закрываются не нами.
- Если чего-то не хватает, приложение открывается именно на этой вкладке — иначе пользователь
  видел бы форму настроек и не понимал, почему ничего не работает.
- Роль «Телефон по умолчанию» не запрашивается и не предлагается: без собственного
  `InCallService` она сломала бы обычные звонки. На вкладке есть пояснение об этом и подсказка
  про автозапуск в прошивках.
- Записи разговоров показываются в настройках (последние пять) и открываются плеером через
  `FileProvider` — записи лежат во внутреннем хранилище, другому приложению нужна content-ссылка.
- Релизная сборка подписывается ключом из `keystore.properties`, если он есть, иначе отладочным:
  приложение ставится вручную, а неподписанный APK установить нельзя. Файл ключа добавлен в
  `.gitignore`.
- В `docs/install.md` — сборка, установка, порядок выдачи доступов, таблица «что проверить на
  телефоне», известные ограничения и диагностика. Рядом лежит тестовый сервер на Go
  (`docs/test-server/main.go`), который печатает приходящие отчёты и умеет возвращать команды.
- Тесты закрывают всю чистую логику: формат времени, сравнение номеров, форму JSON отчёта,
  разбор ответа, окно сбора и защиту от дублей задач. Ничего из этого нельзя проверить на
  живом телефоне без ручных действий, поэтому оно покрыто модульными тестами.

## После обкатки на устройстве (версия 1.1)

### D17. Идентификаторы записей лога не восстанавливаются из файла
Причина: при старте процесса счётчик новых записей начинается с 1, а восстановленные из файла
записи приходят со своими `id`. Пока файл читался в фоне, первые строки новой сессии уже
получали `id = 1, 2, …` — возникали дубли, и `LazyColumn` падал с «Key … was already used».
Следствие: восстановленным записям выдаются отрицательные идентификаторы (они уникальны в
пределах процесса), а список получает их в начало буфера — без изменения порядка «старые →
новые». Положительные номера остаются только за записями текущей сессии.

### D18. Сброс курсоров защищён версией
Сброс курсоров при смене «Начала сбора данных» мог потеряться: если в этот момент шёл обмен,
его успешный ответ записывал курсоры, посчитанные до сброса, и часть данных больше не попадала
в отчёт. Следствие: в служебном состоянии хранится `resetVersion`; обмен запоминает версию на
старте и применяет курсоры только если она не изменилась. Если изменилась — данные уйдут
повторно (сервер отличит повтор по `sync_id`). В карточке «Состояние» показываются окно
следующей отправки и текущие курсоры, в лог обмена пишется, сколько строк прочитано и сколько
отсечено курсорами.

### D19. Трейсы падений сохраняются локально
Системный диалог «Приложение остановлено» отправляет отчёт в сервис Google, а не разработчику,
и после перезапуска трейс недоступен. Следствие: перед передачей ошибки системному обработчику
трейс пишется в `files/crash/last-crash.txt`, а при следующем запуске попадает в лог приложения
под категорией «Сбои» и удаляется. Отдельная категория нужна, чтобы сбой было видно в фильтре,
не листая весь журнал.

### D20. Выборочное копирование логов
«Копировать» копировал только весь журнал. Следствие: на экране логов появился режим выбора:
долгое нажатие на запись включает его, дальше записи отмечаются нажатием (или кнопкой «Все»),
кнопка «Копировать» кладёт в буфер только отмеченные записи. У раскрытой записи есть отдельная
кнопка «Копировать запись». Копируются только записи, видимые с текущим фильтром и поиском:
класть в буфер то, чего пользователь не видит, — сюрприз.
